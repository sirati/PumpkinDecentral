### Locally derived inventory-block actions

- Furnaces, hoppers, and other blocks that change inventories are simulated locally by every peer holding the chunks involved, including secondaries. Every holder deterministically generates the same fallible processing actions.
- These use the same per-tick chunk or joint-chunk buckets, dependency graphs, conflict resolution, undo, replay, Local truth, and Ground truth as other actions.
- Only transmission at creation is suppressed. Neither processing-generated inventory changes nor block-state changes such as a furnace becoming lit or unlit are broadcast. External actions, including player inventory changes, placement, and activation, are communicated normally to the relevant holders.
- Locally generated processing actions otherwise are just regular actions and are treated without any special casing: they remain in the normal retained graphs and are included when those graphs are sent with a requested chunk.
- When an input such as furnace activation arrives for an earlier tick, simulate the affected block through the intervening ticks and insert its locally generated processing actions into the local action backlog at their correct ticks.
- Changes to an input's resolution must propagate through these processing actions and their dependents. If an activation is undone and another action activates the furnace two ticks later instead, the resulting smelting and item-change actions must also move two ticks later. Undo the earlier effects and resolve the correctly timed replacement actions and all affected dependencies through the normal backlog mechanism.
- Visual burn and smelt progress is derived locally from the synchronized inputs and processing history. Timer advancement requires no network update.

## Part 2 — Elaboration (EXPLICITLY LOWER AUTHORITY than the operator's words above; details and hammered-down consequences only)

### 2.1 No locks, no waiting, no replies — what it means in code
- New cluster code uses `mpsc`/`oneshot` fire-and-forget, `try_send`/`try_recv`, owned chunk work, and thread-local bank swaps. Atomics are limited to transport counters and cancellation flags; they do not coordinate gameplay updates. No `Mutex`/`RwLock`/blocking call is allowed on any path that must make progress: tick, login, logout, disconnect, ping, chunk request handling.
- Partition each tick's gameplay work by affected chunk. A single-chunk category owns that chunk and its loaded player/entity state exclusively for its phase. Actions spanning several chunks form one deterministic joint category that owns all participating chunks for that phase. Categories with disjoint chunk sets may execute through Rayon; overlapping categories are ordered by the deterministic action order. Workers return owned results at the phase boundary, so applying updates requires neither shared mutable state nor per-update atomics.
- Waiting for something is forbidden. A peer never waits for an answer to an update because answers do not exist. Arrival of data and arrival of drop/advert notices are inbound events; a recorded single request completes on either event. Anything shaped like request/response, ACK, timeout-then-retry, or await-on-state is a spec violation by construction.
- Disconnects, logins, and status pings make progress with zero chunks available. Awaiting a chunk while holding player or world context is forbidden; presence/logout announces still go out when fetches are pending.

### 2.2 Single action resolution and the ground-truth mechanism
- Every optimistic local action enters the per-tick bucket for the tick it happened in. Peers exchange resolutions; conflicts resolve pairwise through the deterministic per-tick player ordering (`hash(tick .. player)`, ties by server+player id), so 3-way conflicts commute regardless of processing order.
- That existing hash-based, pairwise, order-independent conflict mechanism must converge after incomplete same-tick delivery. Given peers A, B, and C producing conflicting actions a, b, and c, arrivals may initially be A={a,b}, B={b,c}, and C={c,a}, causing different provisional local resolutions. When the missing action reaches each peer during the next tick, every peer must independently settle on the same result by applying the existing conflict mechanism. No resolution exchange or other additional communication is required after delivery of the missing actions.
- An owner-issued entity chunk transition is an infallible action carried on the reliable direct entity channel; player entities use the same mechanism. It is ordered after every other action for its tick and changes the entity's associated chunk only from the next tick onward. Until it advances into ground truth, every holder retains it in a departure index for the chunk the entity left. If actions for the same or a later tick were already recorded against the old chunk association, holders use that retained transition to relocate their chunk references to the new chunk locally, without extra communication. Exactly one peer controls an entity, so competing chunk-transition actions for the same entity cannot exist.
- Each loaded chunk keeps per-tick references to every action concerning it. Entities count as actions of the chunk containing them. An action concerning multiple chunks is referenced by every affected chunk. When a peer has the complete action set from every peer recorded as holding a chunk for that tick, and all prior ticks for the chunk are resolved, it knows locally that the tick can advance into that chunk's ground truth.
- A multi-chunk action d can keep a chunk unresolved while another affected chunk remains unresolved. However, when the existing deterministic conflict mechanism proves that d has lower priority than all relevant single-chunk actions and therefore cannot change the settled result of a, b, and c, a, b, and c may advance into ground truth while the tick remains partially unresolved only for d and its other affected chunks.
- When resolving an action requires state from two or more entities or chunks and a holder lacks part of that state, it sends a settlement-dependency notice to every holder of its local chunk and every holder of each missing entity/chunk. A peer that holds and settles the complete dependency set advances every involved side into ground truth and publishes the settlement to all waiting peers.
- If no peer holds the complete dependency set, notify the primaries that hold portions of it. Those primaries choose one resolution owner using current load, and that owner requests and loads the missing chunks from the other primaries. Once it holds the complete action set and dependency state, it resolves the transaction and publishes the settlement to the waiting peers. The acquired chunks remain loaded for five seconds after settlement.
- A secondary may unload a chunk referenced by an unsettled transaction after its normal drop publication, but a primary that retains any part of the transaction may not unload it until settlement. This ensures that at least one primary retains the complete transaction log so no action is lost. Because holder advertisements already give every peer the holder set for every involved chunk, this coordination requires messages only for dependency waiting, resolution ownership between primaries, and the final settlement.
- After finishing a tick, each peer sends all relevant peers one holistic tick-finish message. It lists, per chunk, every action the sender issued for that tick. Entity actions are listed under the entity's chunk and multi-chunk actions under every affected chunk. Zero-action chunk entries are omitted, but the message itself is holistic: its presence proves that no omitted action from that sender remains outstanding for the tick. Together with the known holder set, this lets every peer determine locally when it has received the complete action set without acknowledgements and without waiting indefinitely for an action that was never issued.
- A valid QUIC connection resumption is a continuation of the existing peer connection. It does not count as a reconnect, replacement, disconnect, membership change, or interruption for synchronization and action-resolution state. A peer is declared dropped after sixty seconds without a keepalive or successful QUIC resumption. A separate new connection authenticating as the same peer is rejected while the existing connection remains active. Such a new connection may be accepted only after the existing connection has produced no keepalive for three seconds. Accepting it starts the dropping procedure for the old connection, and the peer is considered dropped.
- When a peer is declared dropped, every remaining peer broadcasts the chunk/tick pairs for which it still awaits that peer's actions according to a received tick-finish message, plus the chunk/tick pairs for which it received actions from that peer without receiving its holistic tick-finish message. The remaining peers fill the reported gaps from their retained action records, apply every recovered action through the existing deterministic conflict mechanism, mark all remaining chunk/tick gaps as no longer waiting for the dropped peer, and remove the dropped peer from chunk-holder and entity-owner state. Every remaining peer writes an error to its configured log output identifying the dropped peer, the drop reason, and the outstanding chunk/tick gaps reconciled during recovery.
- A tick is globally resolved once every peer known to hold the affected chunks has accepted. Only then are that tick's updates applied at once to the local ground-truth copy. The global tick acceptance is the ONLY confirmation in the system.
- An unresolved acceptance older than ten seconds emits a warning and emits another diagnostic for every further ten-second age band. Once its actual age exceeds sixty seconds, that diagnostic and every later age-band diagnostic use error level. After the last diagnostic for a key, a five-minute cooldown suppresses that key at the same or a lower reported age; reaching a higher ten-second age band still emits immediately. Diagnostics never expire, retry, or mutate the unresolved acceptance.
- State-conditional actions (break with exact expected block type, place against exact target, item-use against exact inventory content) reject cleanly when the world moved under them; the loser path is mechanical, never a re-fetch or a replay.

### 2.3 All fallible actions are undoable; local truth never replays
- Every fallible update (block break/place, redstone, explosion deltas, interaction toggles, inventory ops, dependent comparator/observer firings) carries or references its undo. On conflict loss the peer performs ONLY the undo of the local action, then applies the accepted resolution. Ground truth is never rebuilt from queues and chunks are never resent whole to repair a conflict.
- Because conflicts resolve to iterative updates, clients receive iterative block/inventory deltas even when a fallible resolution changed the outcome — never a full chunk resend as conflict repair.
- Inventory ops are semantic and replayable (source/destination inventory+slot, item, count, op kind), validated against live content so conflicts reject instead of duplicating. Item-use and block-place carry the inventory precondition as one more fallibility axis.

### 2.4 Common mistakes (all observed during v1; treat as review checklist)
- NOT FULLY WIRING: protocol exists and is unit-tested but nothing at runtime calls it — no broadcast hook in the gameplay handler, no delivery/apply task on receive, drained-and-discarded streams. Every producer and every apply path must be proven in RUNNING processes (logs showing serve/fetch/apply/deliver), never by test counts alone. An agent is done only when processes prove the behavior.
- KEEPING CENTRALISED SERVER LOGIC: any design where one server answers, acknowledges, arbitrates, or holds authoritative game state reintroduces the single process through the back door. The primary is disk duty only: no players, no MC listeners, no game decisions. Peers resolve their own players authoritatively; convergence comes from deterministic ordering plus global tick acceptance, never from asking permission.
- GENERATION OR PERSISTENCE ON SECONDARIES: secondaries must be physically incapable of generating a chunk or writing chunks/playerdata to disk; the code path must not exist, not merely be avoided. Same for the primary hosting players or opening game ports.
- SILENT FAILURE PATHS: every bail (decode failure, empty holders, rejected op, dropped chunk) gets a rate-limited log line with the identifiers needed to diagnose it. A failure mode with no log line is a bug.
