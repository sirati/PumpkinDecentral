# Cluster v2 agent operating procedure

The eight subagents own substantial subsystems, not a few files. They work in the shared checkout without worktrees. Current responsibilities are:

| Responsibility | Scope |
| --- | --- |
| Azalea fixture | Local three-process Java E2E, latency, reconnect, packet, global-feature, and log gates; feature-gated test preparation and observations. |
| Controller | Claimed and effective player input, tick-owned controller state, administrative Player effects, and departure drain. |
| Global services | Presence, profiles, permissions, moderation, chat, status, hide, and durable global administration. |
| Inventory ingress | Java and Bedrock packet decoding, semantic input staging, ordering, and authoritative client corrections. |
| Inventory service | Player, entity, block, and virtual inventory truth; semantic operations, menus, screens, and accepted effects. |
| Item actions | Shared item-use and interaction intents, preconditions, conflict resolution, effects, and undo. |
| Lobby and handoff | Virtual lobby, command capabilities, chunk acknowledgements, resume revisions, retention, and packet-safe transitions. |
| World, chunks, and entities | Chunk and actor ownership, holder routing, local and ground truth, settlement, transfer, and world actions. |

Each agent keeps a responsibility and agreement record in `/tmp/pumpkin_agent_coordination/`. Before changing a shared interface or file, its owners agree there on the contract and file ownership. An agent that finds a possible blocker in another agent's scope sends that owner the smallest useful finding, then immediately continues independent work in its own scope. It never waits for the other agent's answer or fix while other assigned work remains. Agents do not acknowledge incoming messages or send progress replies to requests. They answer a request only when the requested work is fully done, with the result and evidence. In particular, the Azalea agent owns the live fixture: after implementing and wiring its full assigned scope, it sends reproducible failures directly to subsystem owners and reruns bounded scenarios after fixes are complete. It does not wait for the main agent to relay ordinary failures or grant each run.

Agents finish and wire their entire assigned subsystem before starting its tests or troubleshooting another subsystem. They resolve routine design choices and source ownership questions with the responsible peer when necessary to keep implementation moving. They do not send the main agent a running feed of small edits, expected compile failures, individual passing tests, or questions that a peer can answer. Each agent batches progress in its `/tmp/pumpkin_agent_coordination/` record and messages the main agent only for a completed request, a material risk to the whole plan, or an unresolved decision crossing responsibilities. A completion report states the behavior delivered and meaningful evidence. Once its fixture is fully wired, Azalea continues the fixture/fix/rerun loop directly with subsystem owners and reports only a material milestone or an impasse.

All local checks, including Azalea and E2E, use Cargo from `nix develop`. `nix build` is reserved for deployment closures. Because all agents share the Cargo target and disk, every Cargo or Nix build/test command holds one shared foreground build lock for its entire duration, for example `flock -x /tmp/pumpkin_agent_coordination/build.lock timeout 900s nix develop -c cargo test ...`. The command exits on completion or timeout. Agents announce long live runs to the other owners and do not inspect detached processes, tmux, or logs repeatedly to monitor progress. A test failure is routed to its owner with the smallest useful evidence; the fixture's strict assertion stays in place unless the expectation itself contradicts the plan.

The main agent keeps the full plan and cross-subsystem completion gates in view and reviews each agent's reviewable checkpoints. A partial checkpoint does not end an agent's responsibility, even if that agent ends its turn or sends a final response: the main agent gives specific review findings and continues the same agent with a follow-up task. The main agent stops an agent and assigns its responsibility to a replacement only after the full scope is complete, the agent cannot continue, or the user directs a replacement. The main agent resolves only decisions that the responsible agents cannot settle together, runs final integration and deployment gates, and reports material outcomes and risks to the user. It does not manage every build-slot handoff, relay routine faults, or comment on each small source change or test result. When independent work is in progress and there is no review or decision to make, the main agent uses a foreground 15-minute terminal sleep and waits for that same command to finish instead of repeatedly polling agents or background processes. Agent messages can still arrive during that interval.

Every agent rereads both `docs/cluster-plan-v2.md` and `docs/cluster-plan-v2-implementation-plan-long.md` after context compaction. Neither plan file is edited without presenting the exact diff and receiving the user's explicit signoff. Agent coordination notes do not amend the plan. New code follows the code-as-docs rule, preserves upstream documentation, and adds behavioral tests rather than tests that merely restate an implementation. A subsystem is complete only when its live producer, transport, receiver, resolution, application, and required regression gates have passed; compiling protocol types alone is not completion.

The plans' ban on locks and waits in cluster progress paths is an entry condition for implementation, not a later cleanup gate. Before wiring a cluster path, the responsible agent audits the reachable call graph, including existing world, player, entity, inventory, and plugin APIs, and uses owned state, bounded messages, or immutable snapshots where a call would lock or wait. If an existing or newly introduced cluster path violates this rule, its owners fix that violation before extending the affected subsystem with more features. A passing compile or E2E scenario does not waive this requirement.

All gameplay action families use exactly one public action submission and application API. An action carries its identity, tick, affected state, conditions, effects, and its own undo procedure. Applying it to the owned state either performs those effects when its conditions hold or returns failure without partial mutation. Resolution sorts first by stakeholder, which is only a chunk or player. The next layer may identify an entity within a chunk or a block or block bounding box; only the layer after that may identify an inventory. Block, player, entity, item, inventory, and world producers construct actions for that same API; family-specific payload formats and constructors do not create separate orchestration pipelines. Keep wire batches grouped by type and preserve deterministic resolution, local and ground truth, and one-way peer delivery. Remove long per-family glue that duplicates capture, routing, conflict, application, or correction decisions.

The reviewed canonical action API is in `docs/unified-action-api-design.md`; editing it requires the human's explicit signoff on the exact diff. Its design owner now implements it and replaces action-specific paths that violate it. The other action-related agents remain paused. They may answer the implementation owner's specific questions, but they perform no source edits, tests, or independent implementation, and then yield again. When the implementation owner considers the migration complete, every expert owner reviews the actual change. The implementation owner fixes every finding and repeats review until every expert reports no remaining nitpick; only then may the implementation owner report completion. Lobby and Azalea work continues independently.
